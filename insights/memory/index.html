Agentic engineering

Memory that doesn't hurt you.

Memory turns a stateless assistant into something that accumulates knowledge. It also turns every mistake into something that persists.

4 min read

Why agents need it

Without memory, every session starts from zero. The agent re-fetches the same data, re-reasons the same conclusions, forgets what the user told it last week, and can't build on another agent's work.

Context decides what an agent knows right now. Memory decides what it knows over time.

Three kinds, three different risks

Working

The scratchpad for this session: tool results, plan state, what has already been tried.

Risk: bloat, and leaking state from one session into another.

Episodic

What happened before: compressed history of past sessions and incidents.

Risk: lossy compression drops the one detail that mattered.

Semantic

What we know: facts, decisions, preferences and domain knowledge.

Risk: stale facts, presented confidently.

Remembering is the easy half

Writing things down is simple. The engineering is in everything around it. Before anything is stored, you should know who owns it, who may read it, where it came from, when it was true, and how it gets removed.

Every memory needs five things: an owner, a scope, a source, a date, and a way to be forgotten.

Who gets to see what

Memory is rarely private to one agent. A system serving a user inside a team usually reads from several scopes and writes to the right one.

ScopeHoldsRead by
AgentInternal state and agent-specific configurationThat agent only
UserPreferences, ongoing tasks, historyAgents acting for that user
TeamShared decisions, runbooks, discovered factsEvery agent in the team, with controlled writes

Getting these boundaries wrong is how one customer's information ends up in another customer's answer.

Where this gets hard

What surprises teams after the demo

Can you find all of it? Raw records are the easy part. Summaries, embeddings and caches derived from them need to go too, and you need to be able to show that they did.

Write-back needs provenance, a confidence level, an expiry and a way for newer knowledge to supersede older. Otherwise the agent's own mistakes become its source of truth.

Anything an agent reads can end up in memory, including content written by someone with bad intentions. Untrusted material shouldn't reach shared memory without a check, and memory needs to be treated as an attack surface.

"Similar" is not the same as "relevant". Filtering by scope and metadata before searching, and measuring how often the right item comes back, matters more than the choice of database.

Shared memory is convenient until concurrent writers disagree. Sometimes a shared store is right; sometimes an explicit handoff between agents is safer. Knowing which is a design decision, not a default.
