Agentic engineering

Workflow, agent, or both?

The most useful question in agentic engineering isn't "which framework?" It's "who decides what happens next: your code, or the model?"

4 min read

Two kinds of system

People use "agent" for everything from a chatbot with a search tool to a system that works unsupervised for hours. The distinction that matters is about control.

  • Workflow: you define the path in code. Models do work at each step, but the sequence is yours.
  • Agent: the model decides the path at runtime: which tool to call, in what order, and when to stop.

Most useful production systems are a third thing: a hybrid. A deterministic workflow provides the structure, and one or two bounded steps inside it are allowed to be open-ended.

It's a dial, not a switch

Reach for the simplest thing that works

PatternA good fit when
Single callThe task is one step and quality is mostly a context problem.
WorkflowYou know the steps in advance and need audit trails and predictable cost.
HybridThe process is fixed, but a step such as investigation or code change is genuinely open-ended.
Autonomous agentThe path can't be predicted, mistakes are recoverable, and you can afford to supervise.

Autonomy trades latency, cost and predictability for flexibility. That's worth paying for sometimes, but it should be a decision with evidence behind it, not a starting assumption.

A rule we use: add a pattern only when the simpler form demonstrably fails. Every extra loop, reviewer or sub-agent is another thing to pay for, test and debug.

Where agents do earn their keep

Some work really can't be mapped in advance. Investigating an incident, or changing an unknown number of files in a codebase, depends on what the previous step found. Here, letting the model direct the process beats any fixed script.

Even then, the model should never be the only thing in charge. It works inside limits that your code enforces: step caps, spend caps, permitted tools, and a defined point at which it hands over to a person.

Where this gets hard

What surprises teams after the demo

Every loop needs ceilings on steps, spend and retries, and a planned fallback for when it hits them: trim context, cut depth, switch to a cheaper model, or ask a person. Cost is a design constraint, not a bill you read afterwards.

Do you retry, resume or undo? That depends on state that survives a crash and on actions that are safe to repeat. It is ordinary distributed-systems work, and it is easy to forget when the exciting part is the model.

Splitting work across agents adds coordination failures. When the final answer is wrong you need to know which agent was responsible, and whether splitting the work was ever worth it.

Frameworks make the first version fast and can hide the prompts and decisions underneath. If nobody on the team can explain what is actually sent to the model, nobody can debug it.
