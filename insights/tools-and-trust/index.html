Agentic engineering

Tools, trust and oversight.

The moment an agent can do things, not just say things, your risk model changes. A wrong answer is an annoyance. A wrong action is an incident.

5 min read

Tools are your business, exposed to a model

Tools are how an agent reads live data, calls APIs and changes things. A badly designed one gives the model a false sense of capability and produces unpredictable results. A few principles go a long way:

  • One job per tool. A tool that can create, update and delete is hard for anyone to reason about, model included.
  • Separate reading from writing. Reads are safe to retry; writes have consequences, and the model should be able to tell which is which.
  • Make writes safe to repeat. If a call times out and is retried, it shouldn't happen twice.
  • Give each tool the narrowest scope it needs.
  • Return errors the agent can act on, not stack traces.

The model proposes. Your code decides.

The safest design treats model output as an untrusted request, and puts deterministic checks between it and anything that matters.

Anything the agent reads can give it orders

A web page, an email or a ticket can contain text that looks like instructions, and a model can't reliably tell data from commands. A sternly worded system prompt doesn't fix this.

The defence is architectural: assume the agent will occasionally be fooled, and make sure a fooled agent still can't do damage. Least privilege, no ambient credentials, limits on what data can leave, and keeping the reading of untrusted content apart from privileged actions.

Match oversight to consequence

Human review isn't a sign that automation failed. It's a control, and it works best when it's reserved for the actions that deserve it.

Read-onlyLook up a deployment statusLog it
Reversible writeOpen a draft pull requestAllow within scope; sample for review
Hard to reverseDeploy, email a customer, change accessExplicit approval, with evidence shown
Irreversible or regulatedPayments, deletions, data exportA person initiates; the agent prepares

A word on MCP

The Model Context Protocol is an open standard for connecting agents to tools and data, and it's a genuinely useful one. It's also a supply chain. The specification itself says tool descriptions should be treated as untrusted unless they come from a trusted server, and that hosts must get user consent before invoking tools.

In practice: decide which servers are allowed, scope the credentials they receive, and review what they expose before an agent can see it.

Where this gets hard

What surprises teams after the demo

An agent acting for a user shouldn't be able to do more than that user can, or more than it was delegated. Identity, permissions and audit trails all have to say who really did what, and agents must not be able to grant themselves access.

If every action needs a click, people stop reading. Approval requests have to carry the evidence and the consequence, and be rare enough to be taken seriously.

Third-party tool metadata is input from someone else. A malicious or compromised description can steer the model. Treat it with the same suspicion as any other external content.

Approvals take human time. The agent has to be able to suspend, survive restarts, and pick up again with the person's decision, without having lost its place.
