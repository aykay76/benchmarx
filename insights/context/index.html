Agentic engineering

Context is the product.

If prompt engineering is how you ask, context engineering is what the system knows when it answers. Most disappointing output traces back to the second one.

4 min read

It usually isn't the model

When an AI result is poor, the model gets the blame. More often the cause is upstream: a business rule nobody wrote down, a stale document, two sources that disagree, or no definition of what "good" looks like.

Fix those and quality improves quickly, and, just as importantly, becomes repeatable across people and tasks.

What counts as context

Instructions

The objective, audience, scope and boundaries.

Reference material

Docs, tickets, decisions, runbooks and policies.

Examples

What good looks like, and what bad looks like.

Constraints

Compliance, style, tooling and technical limits.

Live state

Current code, open work, incidents and recent changes.

Success criteria

The definition of done, and the checks it must pass.

A loop, not a prompt

Good context isn't written once. It's improved after every run, using what the failures reveal.

Three habits that separate the teams that get repeatable results

  1. Treat context as a versioned asset. Briefs, good and bad examples, rubrics and a change log live in the repository next to the code, with an owner.
  2. Decide what wins when sources disagree. The code says one thing and the ticket says another. Choose a precedence, and surface the conflict instead of quietly picking a side.
  3. Budget on purpose. Leave room for the answer, protect constraints and acceptance criteria, and let the model ask for detail on demand rather than stuffing every document in up front.

If you can't explain why an output failed, your context is still too vague. Failure analysis is the fastest way to improve it.

Where this gets hard

What surprises teams after the demo

When the window fills up, something gets cut. Trimming has to be a policy, not an accident: some content is never summarised, and if it can't fit, the right move is to escalate rather than silently drop it.

Model-written summaries can introduce facts that weren't there. Quoting the source with a link is safer than paraphrasing it, and anything summarised needs a trail back to where it came from.

More context is not better context. It raises cost and latency, and gives the model more contradictions to resolve. Deciding what to leave out, and measuring whether retrieval finds the right material, is real engineering.

Context decays like documentation. Without an owner, a review rhythm and a change log, last quarter's rules quietly become this quarter's wrong answers.
